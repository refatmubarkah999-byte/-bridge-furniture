# Bridge Furniture — نظام إدارة الطلبيات

تطبيق ويب (PWA) يعمل على الهاتف والكمبيوتر: موظفو المبيعات يسجّلون الطلبيات، والمالك يرى كل شيء، وإدارة المصنع ترى **سبعة حقول فقط** (رقم الطلبية، الموديل، الصورة، اللون، الكمية، تاريخ التسليم، الحالة) وتغيّر الحالة فقط.

> هذه نسخة تطوير تعمل على بيئة اختبار. **لا تنشرها للعامة ولا تُدخل بيانات زبائن حقيقية** قبل إنهاء مرحلة الجاهزية والموافقة.

## التشغيل على جهازك خطوة بخطوة (Visual Studio Code)

> يعمل المشروع في **Visual Studio Code** (مُوصى به). يمكن فتحه أيضاً في Visual Studio 2022 عبر File → Open → Folder، لكن الأوامر أدناه تُكتب في الطرفية (Terminal) في الحالتين.

### 1) البرامج المطلوبة (مرة واحدة)
- **Node.js** الإصدار 20 أو أحدث (LTS) من nodejs.org
- **Visual Studio Code** من code.visualstudio.com
- عند فتح المجلد سيقترح VS Code إضافات مفيدة (Tailwind، Supabase) — وافق عليها.

### 2) فتح المشروع وتثبيت الحزم
1. فك ضغط الملف، ثم في VS Code: **File → Open Folder** واختر مجلد `bridge-furniture`.
2. افتح الطرفية: **Terminal → New Terminal**.
3. اكتب:
   ```bash
   npm install
   ```

### 3) إنشاء مشروع Supabase للاختبار (مجاني)
1. أنشئ حساباً على supabase.com، ثم **New project** (اختر منطقة أوروبا، مثلاً Frankfurt، لأنها الأقرب).
2. من **Project Settings → API** انسخ: `Project URL` و `anon public key` و `service_role key`.
3. في VS Code انسخ الملف `.env.example` إلى ملف جديد اسمه `.env.local` واملأ القيم الثلاث.
   - ⚠️ مفتاح `service_role` سري جداً: لا ترسله لأحد، ولا ترفعه إلى GitHub (الملف مستثنى تلقائياً).

### 4) بناء قاعدة البيانات
**الطريقة الأسهل (من لوحة Supabase):** افتح **SQL Editor**، والصق محتوى كل ملف من مجلد `supabase/migrations` **بالترتيب** واضغط Run:
1. `20261029000001_schema.sql`
2. `20261029000002_security.sql`
3. `20261029000003_functions.sql`
4. `20261029000004_platform.sql`
5. ثم `supabase/seed.sql` (موديلات تجريبية: Sila، Nola، Lina، Ramah)

**أو عبر سطر الأوامر:**
```bash
npx supabase login
npx supabase link --project-ref <معرّف-مشروعك>
npx supabase db push
```

### 5) إعدادات مهمة في لوحة Supabase
- **Authentication → Sign In / Providers → Email:** أوقف **Allow new users to sign up** (الحسابات يُنشئها المالك فقط)، وأوقف **Confirm email**.
- **Realtime → Settings:** أوقف **Allow public access** حتى تعمل القنوات الخاصة فقط.
- **Database → Extensions:** تأكد أن `pg_cron` مفعّل (لتنبيه الطلبيات المتأخرة يومياً). إن فعّلته بعد تشغيل الملف الرابع، أعد تشغيل الجزء الأخير منه.

### 6) إنشاء حساب المالك الأول
```bash
npm run create-user -- --username owner --name "اسم المالك" --role super_admin
```
سيطلب كلمة المرور بشكل مخفي (10 أحرف على الأقل، حروف وأرقام). باقي الحسابات تُنشأ من شاشة **الموظفون** داخل التطبيق.

### 7) التشغيل
```bash
npm run dev
```
افتح المتصفح على `http://localhost:3000` وادخل باسم المستخدم وكلمة المرور.

**التجربة على هاتفك (نفس شبكة الـ Wi-Fi):**
```bash
npm run dev -- -H 0.0.0.0
```
ثم افتح على الهاتف `http://<عنوان-IP-للكمبيوتر>:3000`. (تثبيت التطبيق على الشاشة الرئيسية وإشعارات الهاتف تحتاج رابط HTTPS، أي بعد النشر.)

### 8) تشغيل اختبارات الأمان
```bash
npm run test:db
```
تعمل على قاعدة PostgreSQL حقيقية داخل الجهاز (بدون إنترنت ولا Docker)، وتطبّق نفس ملفات الترحيل، ثم تحاول من حساب المصنع قراءة كل جدول سري، واستدعاء كل دالة ممنوعة، وتعديل الكمية والسعر والتاريخ مباشرة، وفحص الإشعارات وقناة التحديث الفوري. النتيجة الحالية: **62 نجح، 0 فشل**.

## كيف يحمي النظام بيانات الزبائن من المصنع (بلغة بسيطة)

1. **فصل فعلي للبيانات:** اسم الزبون وهاتفه وعنوانه، والأسعار والدفعات والملاحظات، في جداول منفصلة عن بيانات الطلبية.
2. **حساب المصنع لا يقرأ أي جدول مباشرة:** لا توجد له أي سياسة قراءة. لو حاول أحد التلاعب بالطلبات من المتصفح، تُرجع القاعدة صفر صفوف أو رفضاً.
3. **بوابة المصنع:** دالتا `factory_list_orders` و `factory_get_order` تُرجعان قائمة حقول ثابتة مكتوبة يدوياً — الحقول السبعة فقط.
4. **تغيير الحالة عبر دالة واحدة** `change_order_status`: تتحقق من الدور ومن أن الانتقال مسموح (المصنع: خطوة واحدة للأمام فقط)، وتسجّل التغيير.
5. **الإشعارات والتحديث الفوري والطباعة** تُبنى للمصنع من الحقول المسموحة فقط، والاختبارات تتحقق من ذلك.
6. **الصور** في مخزن خاص، وتُعرض بروابط مؤقتة تنتهي بعد ساعة.

## النشر (لاحقاً، بعد موافقتك فقط)

- الاستضافة المقترحة: **Vercel Pro** (حوالي 20 دولاراً شهرياً) + **Supabase Pro** (حوالي 25 دولاراً شهرياً، يشمل نسخة احتياطية يومية تُحفظ 7 أيام). الخطط المجانية غير مناسبة للتشغيل الفعلي: Vercel المجاني يمنع الاستعمال التجاري، وSupabase المجاني بلا نسخ احتياطية ويتوقف عند عدم الاستخدام.
- مشروع Supabase منفصل للإنتاج غير مشروع الاختبار.
- متغيرات البيئة نفسها تُضاف في إعدادات Vercel (لا في الكود).
- قبل التشغيل: تجربة استرجاع نسخة احتياطية كاملة، وتجربة يوم عمل كامل على Android وiPhone وكمبيوتر.

## الإدارة المالية (التحديث 5)

- ملف قاعدة البيانات: `supabase/migrations/20261029000005_finance.sql` — يُشغَّل مرة واحدة في Supabase → SQL Editor.
- دور جديد **محاسب**: يرى التقارير والدفعات والتكاليف وكل الطلبيات المرسلة، ولا يغيّر الحالات ولا الموظفين ولا الإعدادات.
- **التكاليف**: تكلفة القطعة لكل موديل (`product_costs`)، وتُحفظ نسخة منها مع كل منتج في الطلبية (`order_item_costs`) فلا تتغير أرباح الطلبيات القديمة. الطلبيات التي سُجّلت قبل إدخال أي تكلفة تُحسب بالتكلفة الحالية.
- **الدفعات**: ما يسجّله موظف المبيعات (ومنه العربون) يبقى «بانتظار التأكيد» ولا يُنقص المتبقي حتى يؤكده المالك أو المحاسب.
- **الربح** = المبيعات − تكلفة الموديلات. لا يشمل مصاريف أخرى.
- المبيعات والمصنع لا يرون التكاليف ولا الأرباح بأي طريق (مثبت في `npm run test:db`).

## المرتجعات (التحديث 6)

- ملف قاعدة البيانات: `supabase/migrations/20261029000006_returns.sql` — يُشغَّل مرة واحدة بعد ملف المالية.
- دور جديد **موظف المرتجعات** (`returns`) بحساب مستقل ولوحة خاصة على `/returns`: يُدخل المرتجع بكل تفاصيله (الزبون، المنتج، اللون، الكمية، السعر) ويرسله، ويرى مرتجعاته فقط.
- لا يرى الطلبيات العادية ولا مرتجعات زملائه، لا يحذف، ولا يعدّل أي شيء بعد الإرسال، ولا يصل للإدارة أو المالية.
- المالك يرى كل المرتجعات بأسعارها (فلتر «المرتجعات» في قائمة الطلبيات)، ويتابع حالتها.
- المصنع والمبيعات لا يرون المرتجعات بأي طريق، والمرتجعات لا تدخل في أرقام المبيعات والأرباح (تظهر منفصلة).

## كتالوجات الأقمشة (التحديث 7)

- ملف قاعدة البيانات: `supabase/migrations/20261029000007_catalogs.sql`.
- صفحة **الكتالوجات** للمالك: كتالوجات عامة لكل الموديلات، ولكل كتالوج أرقام ألوان (مع اسم اللون اختيارياً). إيقاف أو حذف لون لا يغيّر الطلبيات السابقة.
- في الطلبية يختار الموظف لكل منتج: الكتالوج ثم رقم اللون. تُحفظ نسخة (الكتالوج + الرقم + الاسم).
- المصنع يرى الكتالوج ورقم اللون على الطلبية وورقة الطباعة.
- الألوان الخاصة بكل موديل صارت اختيارية، وتُستعمل فقط إذا لم توجد كتالوجات.

## بوليصة التوصيل

- زر «بوليصة» في صفحة الطلبية للمالك وموظف المبيعات فقط: باركود رقم الطلبية (Code 128)، بيانات الزبون، المحتوى (مع الكتالوج ورقم اللون)، موعد التسليم، والمبلغ المطلوب تحصيله.
- المبلغ الافتراضي = المتبقي ناقص الدفعات التي تنتظر التأكيد، ويمكن تعديله قبل الطباعة.
- حجمان: A4 (نسختان: للمندوب وللزبون) أو ملصق 10×15 سم. الملاحظات الداخلية لا تُطبع أبداً.

## ملاحظات الطلبية للمصنع (التحديث 9)

- ملف قاعدة البيانات: `supabase/migrations/20261029000009_factory_notes.sql` (آمن للتشغيل أكثر من مرة، بعد ملف الكتالوجات).
- بطلب المالك: ملاحظات الزبون والملاحظات الداخلية تظهر لإدارة المصنع في البطاقة والتفاصيل وورقة الطباعة.
- ما زال المصنع لا يرى اسم الزبون وهاتفه وعنوانه والأسعار والدفعات وملاحظات المنتجات.
- البوليصة لا تطبع الملاحظات الداخلية أبداً (ملاحظات الزبون اختيارية).
